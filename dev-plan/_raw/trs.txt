### 候选方案对比

## 2.5 关键设计原则

原则一：单向依赖，禁止跨层调用。 后端四层中每层只能调用紧邻下层；前端 Components 不直接发起 fetch，必须通过 AppContext 的 dispatch 或封装函数。此规则使各层可独立单测，替换下层实现时上层零改动。
原则二：REST 接口作为前后端唯一契约。 前端不感知后端是否使用 SQLite 还是外部 πOS；后端不感知前端框架版本。双方以本文第 6 章接口规范为唯一对接边界，版本兼容通过响应字段向后兼容保证。
原则三：SQLite 事务边界在 Service 层划定。 所有涉及多表写入（如批量创建任务后更新推荐状态）必须在 Services 层使用 db.transaction() 包裹，Controllers 层及以上不感知事务。better-sqlite3 同步 API 消除了回调/Promise 嵌套导致的事务泄漏风险。
原则四：SSE 优于轮询。 V1 使用 setInterval 短轮询，存在 N 个客户端时产生 N 倍无效请求。V2 后端维护 SSE 连接池，管线状态变更时通过 EventEmitter 单次广播，客户端按需订阅，服务端推送开销与客户端数量线性但低于轮询。当 SSE 连接中断时，usePipelineSSE Hook 内置指数退避重连逻辑。该设计同时满足 SRS NFR-01 的 ≤60s 管线状态同步延迟要求：后端每 5s（默认值，可通过 config.pollingInterval 配置）向 πOS API 轮询一次管线执行状态，状态变更后通过 SSE 流立即推送前端（毫秒级），端到端延迟 ≈ 5s，远优于 SRS 基于双轮询（前端 30s + 后端 30s）所预估的 60s 最坏情况。
原则五：React Context 状态作用域收敛于应用根节点。 本系统无路由分割，所有页面共享同一 AppContext。useReducer 替代 useState 的原因是任务列表、配置、推荐三类状态存在联动 action（如"AI 拆解完成后立即刷新任务列表"），reducer 模式使状态转移可预测、可追踪。
原则六：πOS 对接以环境变量为特性开关。 PIOS_API_BASE_URL 未配置时，piosClient.js 所有方法返回本地 Mock 或直接操作 SQLite，确保系统在无网络环境下完整可用。此设计使 πOS 集成成为可插拔能力而非系统必需依赖。

## 2.7 关键演化接缝

当前架构已在以下位置预留扩展缝隙，未来可在不重构整体结构的前提下局部替换：
接缝 A：数据库层替换（SQLite → PostgreSQL）。 db.js 是整个系统唯一的数据库初始化点，better-sqlite3 的同步调用接口被封装在 Services 层内。若未来需要多进程部署或云数据库，只需将 db.js 替换为异步的 pg 客户端，并将 Services 层的同步调用改为 async/await，Routes 及 Controllers 层不感知此变更。
接缝 B：实时推送升级（SSE → WebSocket）。 当前 SSE 为单向服务端推送。若未来需要双向实时协同，可在后端引入 ws 库替换 SSE 广播模块，前端 usePipelineSSE Hook 切换为 WebSocket 客户端，接口语义不变，AppContext 的 dispatch 逻辑无需改动。
接缝 C：认证层注入（当前无鉴权）。 Express 中间件链在 cors 之后、路由之前预留了中间件插槽。未来可在此位置插入 JWT 验证中间件（如 express-jwt），无需修改任何 Controller 或 Service 代码。前端对应在 AppContext 的请求封装函数中统一附加 Authorization Header。
接缝 D：AI 客户端多供应商切换。 aiClient.js 封装了 OpenAI-compatible 调用接口。若需切换至其他模型提供商，只需修改此单一文件中的 baseURL 与请求格式，aiService.js 调用的 chat() 方法签名保持不变。
> HTTPS 强制要求（第一期生效）：iOS Safari 的 Web Speech API 需要安全上下文（Secure Context），系统须在 HTTPS 域名下部署。HTTP 环境下移动端语音录入功能完全不可用。可选方案：Nginx 反向代理 + SSL 证书、企业内网 HTTPS Web 服务器。第二期 πOS API 代理同样需要 HTTPS 环境。

本章对智能待办事项系统 V2.0 的全栈技术组合进行系统性说明，覆盖选型依据、评分模型、浏览器兼容、依赖许可与风险管控。所有技术均已在本项目代码库中实际落地，不含假设性规划。

## 3.1 技术栈总表


## 3.2 关键技术 5 轴评分

评分轴说明：团队熟悉度（已有实战经验）、生态成熟度（社区/文档/周边工具）、隐性运维（上线后维护负担，5 = 负担最轻）、可替代性（被同类替换的难易度，5 = 最易替换）、与项目约束契合度（MVP、单机、B/S 全栈、开销最小化）。满分 25。
> 说明：Web Speech API 因浏览器兼容性差异（Firefox 支持受限）导致团队熟悉度与生态成熟度评分偏低，但其零成本、零网络延迟的特性使契合度维持在 4 分。

## 3.3 选型论证


### 3.3.1 React 19 + Vite 8（前端框架 + 构建）

选用：React 19 提供成熟 Hooks 生态与并发渲染基础；Vite 8 在开发模式下基于原生 ESM 实现毫秒级热更新，vite build 生产包可由 Express 直接静态托管。
否决：Vue 3 生态同样成熟，但团队 React 积累更深；Angular 17 工程样板过重，不适合 MVP；原生 JS 在组件复用与状态同步上成本过高。
代价：引入 JSX 编译与 node_modules 体积（约 40 MB），对比 V1 单文件无构建方案增加了构建链路复杂度。

### 3.3.2 SQLite + better-sqlite3（数据持久化）

选用：SQLite 无服务端进程，数据库即单文件（todo.db），与 Node.js 同进程；better-sqlite3 同步 API 与 Express 路由处理器风格一致，WAL 模式支持并发读写，可承载本项目的低并发单用户场景。
否决：PostgreSQL 需要独立进程与连接池，运维成本超出 MVP 需要；MongoDB 文档模型对关系型任务数据优势不明显；JSON 文件方案无事务保障，并发写入存在数据损坏风险。
代价：单文件不支持水平扩展；若未来需多用户并发或云端同步，需迁移至 PostgreSQL。

### 3.3.3 Server-Sent Events（实时推送）

选用：SSE 基于 HTTP 长连接，服务端单向推送管线执行状态（pipelineStatus）；浏览器 EventSource 原生支持自动重连；服务端仅需 res.write 与 res.setHeader，零额外依赖。
否决：WebSocket 支持双向通信，但本场景仅需服务端推送，引入 ws 库属于过度设计；短轮询（setInterval）在 V1 已被验证会产生不必要的 DB 查询压力。
代价：SSE 不支持二进制帧；HTTP/1.1 下浏览器同域连接数限制为 6，需注意多标签页场景下的连接竞争。

### 3.3.4 React Context API + useReducer（状态管理）

选用：Context API + useReducer 是 React 内置方案，无额外依赖；AppContext 承载全局任务列表、配置与推荐状态，在单页少路由场景下足够满足需求，调试路径清晰。
否决：Redux Toolkit 样板代码多，对 MVP 规模项目收益低；Zustand 虽轻量但引入额外包与学习路径，增加不必要的依赖。
代价：Context 频繁更新会导致全树重渲染，需配合 React.memo 或拆分 Context 缓解。

### 3.3.5 CSS Modules（样式方案）

选用：CSS Modules 由 Vite 原生支持（*.module.css），提供局部作用域，避免全局命名冲突；相比 V1 的全局 CSS 变量方案显著提升可维护性。
否决：Tailwind CSS 需要扫描 class 名、配置 purge，工具链侵入性强；styled-components 运行时注入影响首屏性能。
代价：组件与 CSS 文件一对一，在组件数量较多时目录层级增加；动态主题切换需额外手段（CSS 自定义变量）配合。

### 3.3.6 Node.js 20 + Express 4（后端运行时与框架）

选用：Node.js 20 LTS 稳定性与安全补丁保障充足；Express 4 中间件生态丰富，cors、express.json() 开箱即用；REST 路由层次（routes → controllers → services）与项目模块划分天然匹配。
否决：Fastify 5 性能更高但 API 风格差异大；NestJS 10 依赖注入框架对 MVP 规模过度封装；Koa 2 缺乏内置中间件，手写量大。
代价：Express 4 无内置类型系统与请求校验，需自行编写入参校验逻辑。

### 3.3.7 OpenAI-compatible Chat Completions API（AI 对接）

选用：aiClient.js 通过 AI_BASE_URL 与 AI_API_KEY 环境变量，可无缝切换 DeepSeek、Moonshot、GPT 等任意 OpenAI-compatible 服务商，具备最高供应商灵活性；无绑定 SDK，仅依赖原生 fetch。
否决：固定绑定 OpenAI 官方 SDK 会引入与服务商紧耦合；自研协议适配层成本超出 MVP 预算。
代价：不同提供商在 system_fingerprint、finish_reason 等字段上存在细微差异，需防御性解析响应体。

### 3.3.8 Web Speech API（语音录入）

选用：浏览器原生，零网络成本，无 API 调用费用；SpeechRecognition 接口提供实时转录流，适合单次任务录入场景。
否决：OpenAI Whisper API 精度更高但每次录音需上传音频文件，引入额外网络延迟与 Token 费用。
代价：Firefox 支持有限（需 media.webspeech.recognition.enable 手动开启）；移动端 Safari 支持度参差，离线场景不可用。

### 3.3.9 原生 fetch() + AbortController（HTTP 客户端）

选用：现代浏览器内置，零依赖；AbortController 与 AI 拆解请求的超时取消逻辑直接集成，代码路径清晰。
否决：axios 1.x 提供拦截器与自动 JSON 序列化，但在本项目中这些能力均可用数行代码替代，引入 axios 属于过度依赖。
代价：fetch 默认不抛出 HTTP 错误状态（4xx/5xx），需手动检查 response.ok，稍增加错误处理模板代码量。

# 4 业务流设计


## 4.1 业务流总览

智能待办事项系统 V2.0 的核心交互围绕五条主要业务流构建。前端 React SPA 通过 REST API 与后端 Express 服务通信，后端持久化至本地 SQLite 数据库（WAL 模式，始终可写，无需离线队列），并通过 SSE 长连接将管线执行状态实时推送至前端。五条业务流如下表所示：

## 4.2 BP-01 录入 → AI 拆解 → 任务创建 → 管线触发


### 4.2.1 主流程

用户通过 InputPanel 以文字输入、语音录制或剪贴板粘贴三种方式提交原始需求文本，前端防抖 300 ms 后向后端发起 AI 拆解请求，后端 aiService 调用 OpenAI-compatible Chat Completions API 将自然语言切分为结构化 DecomposedTask 数组并返回。前端弹出 TaskReviewModal 供用户确认、编辑或删减子任务，确认后批量调用 POST /api/tasks 逐条落库，最后调用 POST /api/pipelines/trigger 向 πOS 提交执行，触发成功后 SSE 广播初始状态。
> 步骤顺序说明：①逐条 POST /api/tasks 创建任务（pipelineId=null）→ ②如用户选择关联管线，PATCH /api/tasks/:id 写入 pipelineId → ③ POST /api/pipelines/trigger {pipelineId} 触发执行 → ④返回的 executionId 通过 PATCH 写回对应任务
图 6　图4-1 BP-01 录入→AI拆解→任务创建→管线触发主流程时序图

### 4.2.2 异常分支

AI 超时或请求失败：aiService 设置超时阈值（默认 30 秒）。超时或 HTTP 非 200 时，降级为按标点符号（句号、逗号、换行符）分割原始文本，每段生成一条 DecomposedTask，name 取原始文本段，priority 默认 medium，category 为空。降级结果与正常 AI 返回具有相同的 DecomposedTask[] 结构，TaskReviewModal 正常弹出，界面显示 Toast 提示"AI 拆解超时，已按标点分割"。
批量创建局部失败：任务逐条 POST，若某条返回 4xx/5xx，前端跳过该条并记录失败数量，继续创建其余任务。全部请求完成后，Toast 汇总显示"成功创建 N 条，失败 M 条"。已成功入库的任务不受影响，失败的任务可由用户手动重试。
管线触发失败：若 POST /api/pipelines/trigger 返回错误或 πOS 不可达（PIOS_API_BASE_URL 未配置），任务已正常写入 SQLite，pipelineStatus 字段保持 null。前端显示 Toast "任务已创建，管线触发失败，可稍后重试"，ConfigPanel 提供手动重触发入口。

### 4.2.3 补偿流

AI 降级路径返回与正常路径完全相同结构的 DecomposedTask[]，下游无需区分。管线触发失败时，SQLite 中任务记录已存在且 pipelineStatus=null，系统状态一致性由 SQLite 事务保证；用户可在任务详情中点击"重新触发"，再次调用 POST /api/pipelines/trigger，不会产生重复任务。SQLite 始终可写，无需离线队列，任何失败都不会丢失已录入的数据。

## 4.3 BP-02 管线状态 SSE 推送 → 任务状态联动


### 4.3.1 主流程

后端 Express 挂载专用 SSE 端点 GET /api/pipeline/status-stream，响应头设置 Content-Type: text/event-stream。piosClient 以定期轮询方式（默认 5 秒）调用 GET /api/pipelines/:id/executions/:execId 获取最新执行状态，状态变更时通过 Node.js EventEmitter 广播，SSE 中间件将事件写入所有已连接的 EventSource 客户端。前端 usePipelineSSE Hook 在组件挂载时建立 EventSource 连接，收到消息后向 AppContext 派发 UPDATE_TASK_STATUS action，React 状态更新驱动 TaskItem 重新渲染；当管线状态变为 completed 时，前端同步将 Task.status 置为 completed。
图 7　图4-2 BP-02 管线状态SSE推送→任务状态联动主流程时序图

### 4.3.2 异常分支

EventSource 断线重连：浏览器原生 EventSource 在连接断开后自动重连（默认退避约 3 秒），无需前端额外处理。重连后后端立即推送最新已知状态，确保前端状态最终一致。
πOS 不可达：piosClient 轮询请求失败时，后端停止向 EventEmitter 广播新事件，已连接的 EventSource 不会收到新消息。前端 TaskItem 显示上次已知的 pipelineStatus，不会出现错误提示循环。若 piosClient 连续失败超过阈值（默认 3 次），后端记录日志并将该 executionId 的轮询暂停 60 秒，防止频繁无效请求。
SSE 连接超时：部分反向代理或负载均衡会断开长连接，usePipelineSSE 监听 EventSource.onerror 事件，重新创建 EventSource 实例并恢复订阅，保证页面刷新内的持续监听。

### 4.3.3 并发控制

SSE 推送的 pipelineStatus 更新携带服务端 updatedAt 时间戳。AppContext reducer 在处理 UPDATE_TASK_STATUS 前比较 payload.updatedAt 与 store 中该任务现有 updatedAt：若 payload.updatedAt ≤ 现有值，则丢弃本次更新，防止乱序消息或用户手动修改状态（本地 updatedAt 更新）被 SSE 旧消息覆盖。

## 4.4 BP-03 高频任务分析 → 推荐生成 → 采纳/忽略


### 4.4.1 主流程

用户在 ConfigPanel 点击"立即分析"或系统定时触发，前端调用 POST /api/ai/analyze。后端 recommendationService 首先查询 SQLite tasks 表，按 category/keyword 统计频率，过滤出出现次数超过阈值（默认 3 次）且尚无对应管线的模式；将符合条件的高频模式批量送入 AI 接口生成推荐内容（suggestedPipelineName、suggestedKeywords、reason）；结果写入 recommendations 表，状态设为 pending，同时更新 config 中的 analyzerLastRunAt。前端 RecommendationPanel 轮询 GET /api/config/recommendations 展示待处理推荐卡，用户可采纳（accept）或忽略（dismiss）。
图 8　图4-3 BP-03 高频任务分析→推荐生成→采纳/忽略主流程时序图
> 采纳操作语义说明：采纳操作（status=accepted）仅将 Recommendation 状态更新为 accepted，并将 suggestedKeywords 作为 keywordRule 关联至已存在的管线（通过 suggestedPipelineId 匹配）；不自动创建新管线——用户须在 ConfigPanel 手动创建管线后再关联。若 suggestedPipelineId 对应的管线尚不存在，keywordRule 将写入 orphan 状态，等待用户在 ConfigPanel 手动完成管线创建与绑定。

### 4.4.2 异常分支

AI 分析请求失败：aiService 调用 OpenAI 接口失败（超时或非 200）时，recommendationService 不向 recommendations 表写入任何记录，但仍将 analyzerLastRunAt 更新为当前时间，避免短期内重复触发高代价分析。后端向前端返回 200 并附带 {count: 0, error: 'ai_failure'}，Toast 显示"分析完成，AI 推荐暂时不可用"。
频率门控无结果：若 tasks 表中所有模式均未达到阈值，recommendationService 直接跳过 AI 调用，返回 {count: 0}，不产生无效推荐。
采纳时 keywordRule 写入失败：PATCH 操作中，recommendations 状态更新与 keywordRule 写入在同一 SQLite 事务内执行，任一步失败则整体回滚，推荐状态维持 pending，前端 Toast 显示"采纳失败，请重试"。

### 4.4.3 补偿流

忽略操作设置 suppressUntil 字段（当前时间戳 + 7 天毫秒数），下次分析时 recommendationService 跳过 suppressUntil > NOW 的 patternSignature，避免对用户已明确拒绝的模式重复推荐。analyzerLastRunAt 无论 AI 是否成功均会更新，保证分析节奏稳定。

## 4.5 BP-04 管线创建 → 关键词规则绑定


### 4.5.1 主流程

用户在 ConfigPanel 的管线配置区域填写管线名称与关键词规则，点击"创建管线"。前端调用 POST /api/pipelines，后端 pipelineController 调用 piosClient.createPipeline() 向 πOS 提交创建请求；πOS 返回新管线的 pipelineId。创建成功后，后端立即在同一请求处理链中调用 PATCH /api/config，将用户指定的触发关键词写入 Config.keywordRules，关联新创建的 pipelineId。前端收到 201 响应后刷新 ConfigPanel 管线列表，新管线与关键词规则即时生效，后续任务录入时 AI 路由模块将参照此规则匹配。

### 4.5.2 原子性保障与回滚

管线创建与关键词规则绑定不在同一服务实体（πOS 为外部系统），无法通过单一数据库事务保证原子性，采用以下顺序补偿策略：
调用 piosClient.createPipeline()，失败则直接返回 500，不写入 config，ConfigPanel 提示"管线创建失败"。
piosClient 成功返回 pipelineId 后，调用 configService 在 SQLite 事务内写入 keywordRules。若此步失败，后端记录 {pipelineId, pendingKeywords} 至 config 中的 orphanPipelines 列表，并返回 207 Partial Success。前端 Toast 显示"管线已创建，关键词绑定失败，请在配置页手动绑定"，ConfigPanel 加载时检测 orphanPipelines 列表并高亮提示未绑定的管线。

### 4.5.3 异常分支

πOS 不可达：PIOS_API_BASE_URL 未配置或请求失败，后端降级创建一条本地占位管线记录（仅写入 SQLite config，pipelineId 生成本地 UUID，标注 localOnly=true），关键词规则正常绑定至本地管线。待 πOS 恢复后，用户可在 ConfigPanel 手动同步本地管线至 πOS。
关键词规则冲突：若提交的 keywords 与已存在 keywordRule 重复，configService 合并规则（同一 keyword 指向最新 pipelineId），不报错，返回合并后的完整规则集。

## 4.6 BP-05 基础 CRUD（内联编辑 / 删除 / 筛选）


### 4.6.1 主流程

TaskListPanel 在页面初始化时调用 GET /api/tasks 获取全量任务列表，后端从 SQLite 查询并按 createdAt DESC 排序返回。前端将任务列表存储于 AppContext state，所有后续操作以乐观 UI 模式进行：前端先更新本地 state，再将变更异步提交后端，失败时回滚。
内联编辑：用户双击 TaskItem 进入编辑模式，修改 name/priority/category/dueAt 等字段后失焦保存。前端先更新 AppContext 中该任务对象，再发送 PATCH /api/tasks/:id；后端 taskService 以 SQLite 事务更新对应行，同时刷新 updatedAt 字段；返回 200 后前端以服务端返回值替换本地乐观副本，保证 updatedAt 同步。若 PATCH 失败，前端回滚至编辑前值并显示 Toast 错误。
删除：用户点击 TaskItem 删除按钮，弹出确认对话框；确认后前端从 AppContext 列表中移除该项（乐观），发送 DELETE /api/tasks/:id；后端执行 SQLite DELETE，返回 204；若失败，前端重新插回列表并 Toast 提示。
筛选/排序：TaskListPanel 提供状态（pending/completed）、优先级（low/medium/high）、分类筛选及按 createdAt/dueAt/priority 排序。筛选与排序均为前端纯内存操作，基于 AppContext 中已加载的任务列表，不触发新的 API 请求，保证交互无感延迟。

### 4.6.2 SQLite 作为唯一真值源

V2.0 移除了 V1 中的 localStorage 持久化和离线队列（todo_task_queue）。所有任务数据以 SQLite 为唯一真值源，页面刷新后通过 GET /api/tasks 重新加载，保证多标签页状态一致。better-sqlite3 同步 API 在 WAL 模式下写入延迟极低（通常 < 1 ms），乐观 UI 的回滚概率极小。

# 5 数据流设计


## 5.1 四段管道总图

系统数据流以"来源 → 变换 → 落地 → 出口"四段管道为骨架，覆盖用户录入、AI 推理、管线状态同步、配置读写四条主干链路。所有持久化操作均以 SQLite 为唯一后端存储，前端以 React Context（AppContext + useReducer）维护内存态视图。
图 9　图5-1 四段管道数据流总图
四段含义说明：
来源：用户交互事件（文字/语音/粘贴）、外部 AI 接口、πOS 执行状态接口、ConfigPanel 表单提交，是所有数据的原始入口。
变换：Express 路由层完成请求合法性校验，Service 层负责字段映射、AI 响应解析、N-gram 频率分析等业务逻辑，不直接操作数据库。
落地：所有持久化写入均落入 SQLite 三张表；better-sqlite3 同步 API 保证调用栈简洁、无回调嵌套。

## 5.2 数据链路详解


### DL-01 用户录入 → SQLite 持久化

链路路径
InputPanel（form / voice / paste）
  → POST /api/tasks（JSON body）
    → Express 校验（name 非空、枚举字段合法）
      → taskService.create()（生成 id、createdAt、updatedAt）
        → SQLite INSERT INTO tasks
          → 201 响应（完整 Task 对象）
            → AppContext dispatch ADD_TASK
              → TaskListPanel 重渲染
字段映射表
PATCH 请求的字段更新规则相同，updatedAt 由后端强制覆写为当前毫秒时间戳，防止客户端伪造。

### DL-02 AI 拆解链路

链路路径
InputPanel 用户输入文本
  → POST /api/ai/decompose（body: { text }）
    → aiService.decompose()
      → 截断至 4000 字符（防止 token 溢出）
        → OpenAI Chat Completions API（temperature=0.4）
          → 响应 JSON 解析 → DecomposedTask[]
            → TaskReviewModal 展示确认
              → 用户批量确认
                → 逐条调用 DL-01 写入路径
AI 请求构造
系统提示（system prompt）约定返回格式为 JSON 数组，每项包含 name、priority、category、timeLabel 字段。
用户消息（user message）为截断后的原始输入文本（上限 4000 字符）。
temperature=0.4：保持语义忠实，允许适度补全任务名称。
解析容错（降级策略）
JSON 解析失败时，aiService 执行标点分割降级：
原始文本 → 按"。！？；\n"分割 → 过滤空字符串
  → 每段作为独立 Task.name
    → source 标记为 "ai"
降级结果同样推入 TaskReviewModal，用户仍可在确认前手动编辑。

### DL-03 管线状态同步链路（SSE）

链路路径
后端定时轮询（setInterval）
  → piosClient.getExecutionStatus(pipelineId, executionId)
    → πOS Execution API 响应
      → 比对本地 tasks.pipelineStatus
        → 若状态变更 → EventEmitter.emit('pipeline-status-update', payload)
          → SSE 处理器 res.write(...)
            → 前端 EventSource onmessage
              → usePipelineSSE hook 解析 data
                → AppContext dispatch UPDATE_TASK_PIPELINE_STATUS
                  → TaskItem 状态徽章重渲染
SSE 事件格式
每条事件遵循 W3C Server-Sent Events 规范，单个数据帧格式如下：
data: {"taskId":"uuid-xxxx","pipelineStatus":"running"}\n\n
data: 字段为 JSON 字符串，两个换行符 \n\n 标识事件边界。
pipelineStatus 取值范围：triggered / running / completed / failed（含义见附录 B 状态机）。
响应头固定为 Content-Type: text/event-stream，Cache-Control: no-cache，Connection: keep-alive。
客户端订阅生命周期
usePipelineSSE hook 在组件挂载时创建 new EventSource('/api/pipeline/status-stream')，在卸载时调用 eventSource.close()，避免内存泄漏。πOS 未配置（PIOS_API_BASE_URL 为空）时，后端仍保持 SSE 连接但不发送任何事件，前端保持空闲等待而不报错。

### DL-04 频率分析 → 推荐链路

链路路径
POST /api/ai/analyze（手动触发或 ConfigPanel 定时触发）
  → recommendationService.analyze()
    → SQLite SELECT tasks WHERE createdAt > NOW()-90天
      → tokenize（分词） + N-gram（2-gram、3-gram）统计词频
        → 过滤规则：
            90 天内已有同签名推荐 → 跳过
            suppressUntil > NOW() → 跳过（7 天抑制期）
          → 候选模式列表
            → OpenAI batch 请求（temperature=0）生成推荐理由
              → SQLite INSERT INTO recommendations
                → GET /api/config/recommendations
                  → RecommendationPanel 展示推荐卡
分析参数
分析窗口：90 天内的历史任务（analyzerWindowDays = 90，可在 ConfigPanel 调整）。
最低频次阈值：同模式出现 ≥ 3 次方进入候选（analyzerFrequencyThreshold = 3，可配置）。
AI 请求 temperature=0：推荐理由需要确定性输出，避免语义漂移。
patternSignature 由 N-gram 排序后的关键词拼接而成，用于去重判断。
suggestedKeywords 以 JSON 字符串形式存储（如 '["汇报","周报"]'），读取时由 Service 层解析为数组再返回前端。
用户操作回写
用户在 RecommendationPanel 点击"采纳"或"忽略"后，前端调用 PATCH /api/config/recommendations/:id，后端更新 recommendations.status 并在忽略时将 suppressUntil 设为 Date.now() + 7*24*3600*1000。
N-gram 分词规则：tokenize 按空格与标点（。！？；—）分割任务名称，保留长度≥2的词；生成2-gram与3-gram（示例："完成技术文档"→tokens=["完成","技术","文档"]，2-gram=["完成技术","技术文档"]，3-gram=["完成技术文档"]）；frequency[ngram]≥analyzerFrequencyThreshold（默认3）进入候选；patternSignature = 候选 ngram 排序后按"|"拼接，用于去重。

### DL-05 配置读写链路

链路路径
ConfigPanel 表单提交
  → PATCH /api/config（body: { aiApiKey, aiBaseUrl, piosToken, ... }）
    → configService.updateConfig()
      → db.transaction()：逐键 SQLite UPSERT config 表
        → 写入完成后 sync process.env（aiApiKey → OPENAI_API_KEY 等）
          → configService.getSafeConfig()
              → 脱敏：omit aiApiKey，add hasApiKey: boolean
                → 200 响应脱敏配置对象
                  → ConfigPanel 回显（不展示明文密钥）
安全脱敏规则
aiApiKey 仅写入 SQLite，响应体中以 hasApiKey: true/false 替代；前端只展示"已配置"状态，不回显明文。
piosToken 同理，响应体字段名为 hasPiosToken。
GET /api/config 同样经过 getSafeConfig() 脱敏，保证任何读取路径均不泄露密钥。

## 5.4 SQLite 事务边界

better-sqlite3 的同步 API 支持显式事务包裹（db.transaction(fn)(args)），系统在以下场景中明确界定事务边界：
WAL 模式优势：系统初始化时执行 PRAGMA journal_mode = WAL，WAL 模式下多个读事务可与写事务并发进行，互不阻塞。对于前端并发调用 GET /api/tasks 与后台 SSE 状态写入的场景，WAL 模式避免了读写互斥导致的接口延迟。
并发写入处理：WAL 模式下写入仍需顺序化，多个并发请求可能触发 SQLITE_BUSY。db.js 初始化时设置 db.pragma('busy_timeout = 5000')，自动重试最多 5 秒；超时后返回 503，前端乐观 UI 回滚。单用户场景下此场景极少发生。

# 6 后端接口设计


## 6.1 接口风格约定


### 6.1.1 URL 命名规则

所有内部接口均以 /api/ 为前缀，资源名称使用复数小写名词（tasks、pipelines、config），AI 功能集中在 /api/ai/ 命名空间下，管线实时流单独挂载于 /api/pipeline/status-stream（单数，区别于管线资源集合）。路径参数采用驼峰命名（:id、:pipelineId、:executionId）。

### 6.1.2 HTTP 方法语义

系统不使用 PUT（整体替换），所有更新均通过 PATCH 发送差量字段。

### 6.1.3 统一响应格式

成功响应：Content-Type: application/json，正文为资源对象或资源数组。
错误信封：
[json]
{
  "error": {
    "code": "TODO_E_INPUT_001",
    "message": "字段 name 不能为空"
  }
}
所有错误均使用此二层结构，code 为机器可读标识符，message 为可读描述。

### 6.1.4 标准 HTTP 状态码


### 6.1.5 局部更新（PATCH）约定

PATCH 请求体只包含需要修改的字段，后端忽略未传字段（保留原值）。不可修改字段（id、createdAt）即使出现在请求体中也被静默忽略。后端在每次 PATCH 成功后自动将 updatedAt 设置为当前 Unix 毫秒时间戳。

### 6.1.6 分页

当前版本面向单用户本地场景，任务上限设计为 500 条以内，SQLite 单次全量查询即可满足性能要求，GET /api/tasks 不支持分页参数。

### 6.3.8 GET /api/pipeline/status-stream

用途：长连接 SSE 端点，前端 usePipelineSSE Hook 通过 EventSource 订阅，获取待处理任务列表的实时推送。
响应头：
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
SSE 事件格式（数据推送）：
data: {"tasks":[{"id":"task_xxx","name":"完成文档","status":"pending","pipelineStatus":"running","executionId":"exec_001","updatedAt":1716990000000}],"timestamp":1716990000000}
心跳帧格式（每 30 s 发送，防止代理超时）：
: heartbeat
连接生命周期：
连接建立时立即发送一次当前待处理任务快照。
此后每 5 s 轮询 SQLite，推送 status='pending' 或 status='running' 的任务列表。
客户端断开（req 触发 close 事件）→ 服务端清除 setInterval，调用 res.end()。
计时器说明（两个独立计时器）：
数据推送计时器：每 5 秒（pollingInterval）查询 πOS/SQLite 执行状态，若有变更立即推送 SSE 数据帧；无变更则本周期内不发送任何帧（避免冗余数据）。
心跳计时器：独立于数据推送计时器，连续 30 秒无数据帧推送时发送 : heartbeat\n\n，防止反向代理因连接空闲断开 TCP；有数据帧推送时心跳计时器重置。
SSE 推送时机：
轮询检测到状态变更 → 立即推送 SSE 数据帧，不等待下一个 5 秒轮询周期。
轮询周期内无状态变更 → 不发送空帧，避免冗余数据传输。
客户端重连：浏览器 EventSource 在连接断开后自动携带 Last-Event-ID 重连，服务端无需实现事件持久化（当前实现不使用 id: 字段）。
πOS 执行状态别名映射：
轮询 GET /api/pipelines/:id/executions/:execId 时，πOS 可能返回多种状态字符串别名，系统统一按以下规则映射后写入 Task.pipelineStatus：
失败处理：若 SQLite 查询异常，将错误信息封装在 data 中推送（{ error: "...", timestamp: ... }），连接不中断。

## 6.5 鉴权与安全


### 6.5.1 内部 API 无鉴权

Express 后端的内部 REST API（/api/*）面向单机部署场景，所有端点不携带认证逻辑。前端与后端运行在同一主机或同一受控内网，通过 CORS 来源白名单限制访问。

### 6.5.2 外部服务 Bearer Token

AI 服务密钥（aiApiKey）和 πOS 令牌（piosApiToken）仅在调用对应外部服务时注入请求头：
AI 调用：Authorization: Bearer <aiApiKey>（由 aiClient.js 注入）
πOS 调用：Authorization: Bearer <piosApiToken>（由 piosClient.js 注入）
两个密钥存储于 SQLite config 表，永远不出现在 GET /api/config 的响应体中。仅有 hasApiKey（boolean）和 hasPiosToken（boolean）两个脱敏指示字段对外暴露。

### 6.5.3 CORS 配置

服务端通过 cors 中间件严格限制跨域来源：
origin: process.env.FRONTEND_URL  （默认 http://localhost:5173）
methods: GET, POST, PATCH, DELETE, OPTIONS
allowedHeaders: Content-Type, Authorization
credentials: true
生产部署时须将 FRONTEND_URL 精确设置为前端实际域名，杜绝通配符来源。

## 6.6 限流 / 重试 / 幂等性


### 6.6.1 频率分析节流

FrequencyAnalyzer 通过 analyzerLastRunAt 与 analyzerThrottleMs（默认 3 600 000 ms，即 1 小时）的差值实现节流。每次 POST /api/ai/analyze 调用均先在服务层进行本地时间比对，未达阈值则直接返回空数组，不发出任何 AI 请求。

### 6.6.2 AI 请求超时

所有 AI 调用经由 aiClient.js 统一包装，使用 Node.js 原生 AbortController 实现 30 秒强制超时。超时后触发 AbortError，上层服务捕获后视场景执行降级或返回 503。

### 6.6.3 πOS 请求重试

piosClient.js 调用 πOS 接口时，对 5xx 响应执行最多 2 次重试，每次重试前等待 1 秒退避。401 错误不重试，直接上抛。重试耗尽后以 TODO_E_PIOS_002 报错。

### 6.6.4 任务创建幂等性

POST /api/tasks 支持客户端提供 id 字段。TaskReviewModal 批量创建时，若因网络抖动需要重试，前端携带相同 id 再次请求，SQLite 主键约束保证不会写入重复记录。

### 6.6.5 πOS 创建任务幂等性

piosClient.createTask 在每次调用时生成唯一 Idempotency-Key（UUID v4）并通过请求头传递给 πOS，πOS 端依此实现幂等去重。

### 6.6.6 SSE 心跳

GET /api/pipeline/status-stream 端点使用两个独立计时器：数据推送计时器（每 5 秒轮询，有变更时推送数据帧）和心跳计时器（连续 30 秒无数据帧推出时发送 : heartbeat\n\n）。两个计时器相互独立，心跳计时器在每次成功推送数据帧后重置，以防止反向代理因连接空闲断开 TCP 连接。正常轮询周期内有数据推送时，心跳帧不会在同一时间窗口内额外发送。

## 6.8 版本策略

内部 REST API（/api/*）为单实例部署，不设版本前缀，无兼容性演进需求。路由命名保持稳定，若需破坏性变更需整包升级部署。

AI 模型版本由 AppConfig.aiModel 字段控制，通过 PATCH /api/config 动态切换，无需代码变更即可升级或降级模型。当前默认值为 gpt-4o-mini。
